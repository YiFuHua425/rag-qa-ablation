## 4.2 运行环境（及一个必须说明的偏离）

计划阶段预期"单卡 8G（RTX 4070 Laptop）"。实际执行中**所有数字都在 CPU 上产出，GPU 从未参与**——原因是两层，必须分开说清：

1. **检索侧的 torch 装不上**：250 MB 轮子在镜像下反复超时（pitfalls #11），整条稠密链改走 onnxruntime + int8 ONNX。组内因此没有一台机器装的是 CUDA 版 torch。
2. **重排与阅读器虽装了 torch，但延迟口径被刻意固定为 CPU 单线程**（见 4.4 节）：一是跨机器可比，二是对应"无显卡部署"这一常见场景。

需要强调的是：**"没用 GPU" 不等于 "没有 GPU"**。复核时发现，A 的机器就是那块 8G 的 RTX 4070 Laptop，只是装的是 CPU 版 torch（`torch.cuda.is_available()=False`），所以 `rerank.device=cuda` 会静默退回 cpu。这不是环境缺失，而是**没有为 GPU 单独适配**——一个真实且常见的工程状态。

| 项 | 实际情况 | 影响 |
|---|---|---|
| GPU | **有硬件、未启用**（A 机为 RTX 4070 Laptop 8G；但装的是 CPU 版 torch，`cuda.is_available()=False`，`device=cuda` 静默退回 cpu） | 延迟是 CPU 单线程口径，不代表 GPU 上的可用性 |
| 稠密编码 | **onnxruntime + int8 ONNX**（BGE-small-zh-v1.5，22.8 MB） | 绕开 torch（250 MB 轮子反复下载失败） |
| 交叉编码器 | **torch + fp32**（bge-reranker-base，1.1 GB） | 与编码器不同框架，见 4.5 节第 6 条 |
| 阅读器 | torch + fp32（roberta-base-chinese-extractive-qa，407 MB） | 最贵的一段，E4/E5 因此只用 100 题 |
| 向量索引 | faiss-cpu 1.16.0，保留 numpy 兜底 | 两后端 top-100 集合 100% 一致 |
| Python | 3.14.5（D 机）/ 3.12.10（A 机）/ 3.10–3.11 venv（B/C 机） | 3.14 无 torch/faiss wheel，故组内不统一 |

> **一个诚实的偏离**：组内两台机器的依赖栈不同（B 走 onnxruntime，C 走 torch）。为了保证 E4/E5 与 E2/E3 可比，C 的做法是**直接复用 B 缓存的候选集合**（`E2_rrf_alpha0.2.json` 的 `per_question[].ranked`），而不是用自己的编码器重跑检索。这一点是第 5 章跨实验比较成立的前提；若各自重跑，检索侧 0.44 个点的量化差异会混进重排结论里。

## 4.3 数据构建

`data/build_data.py` 把 CMRC2018 的 squad-style json 转成两个 jsonl。产出的每个数字都可复算（`data/raw/build_stats.json` 留档）：

| 项 | 数值 | 说明 |
|---|---|---|
| 语料段落 | **3507** | train 2403 + dev 848 + trial 256，三份**零重叠** |
| 评测问题 | **3219** | dev 全部保留，0 题被丢弃 |
| 金标段落数 | **848** | 每题唯一金标；同一段落被多题复用 |
| 段落长度 | 均值 509.1 字，最长 980 字 | 超过 512 token 上限 → 必须滑窗（4.5 节第 4 条） |
| 答案长度 | 均值 10.7 字 | 短答案，F1 对边界敏感 |
| `answer_start` 校正 | **3 题** | 原始标注偏移，用 `context.find()` 重算 |
| 答案越界 / 金标缺失 | **0 / 0** | `check_data.py --strict` 断言 |

三项数据处理决定及其理由：

1. **不信 `answer_start`，一律重算**。squad-style 的 dev 里有 3 题的 `context[start:start+len(answer)]` 对不上，若直接沿用，阅读器的监督对齐与 E5 的"金标定位"都会错位。用 `context.find(answer_text)` 重算并把偏移数单独记账。
2. **段落跨 split 去重后统一编号**。先到先得（train → dev → trial），保证同一段落永远得到同一 `doc_id`。
3. **一题多答案取 `answers[0]`**。CMRC dev 每题给 3 个答案（内容通常相同），取第一个与 SQuAD 官方口径一致；代价是若三者真有差异，F1 会略偏保守（这条留作改进方向）。

**数据闸门**：`eval/check_data.py` 把上述约束写死为四项断言，任何一项不过即 `exit 1`，从机制上防止"用错数据跑完所有实验"。

## 4.5 六个非平凡的实现细节

以下六条都是"照论文写会踩、踩了还不报错"的地方，也是本章最值得记录的部分。

### 4.5.1 L2 归一化必须显式透传

ONNX 编码器的导出图内部**默认已做 L2 归一化**，外部再传 `normalize=False` 会被图内部吞掉 —— 两臂结果完全相同，做归一化消融时会白跑。解法是给编码器加 `normalize` 参数透传到图内，并让**向量缓存键带上 `norm/raw` 标记**，否则会命中另一臂的缓存。

实测影响（E1 对照）：不归一化时单路 Recall@5 0.9487 → 0.9366（−1.2 个点），MRR −2.4 个点；融合后 Recall@5 几乎不变但 MRR 仍掉 0.24 个点。

### 4.5.2 向量缓存键必须锚定语料内容

第 1 棒的数据曾把 `doc_id` 从 `p_00000` 起改成 `p_00001` 起（条目数仍是 3507）。旧缓存的命中条件是"向量条数相同"，于是**旧向量被贴到新 doc_id 上，指标会偏但没有任何报错**。

解法：缓存文件名带语料内容的 sha1 前 12 位（`emb_docs_...-<digest>.npz`），npz 内再存一份 `digest`，命中时双重校验。**教训：凡是"能被静默复用"的中间产物，其键必须锚定输入内容，而不是输入的形状。**

### 4.5.3 BM25 的分词器必须与模型一起冻结

同一套 E2 配置，用"单字 + 二元组"分词时 α 曲线**单调下降**（结论会是"融合无用"）；换 jieba 精确分词后变成"中间高两头低"（α=0.2 最优）。

**分词器改变可以反转结论**，因此分词器配置写进 `config.yaml`、并随 BM25 的序列化文件（`to_dict/load`）一起保存 —— 否则加载后分数会静默错位。

### 4.5.4 阅读器：滑窗 + 只接受上下文侧 token

两个问题：

1. **不滑窗 = 一半答案在窗外**。段落均值 509 字 ≈ 700 token，`max_length=512` 直接截断会切掉段落后半（常常正是答案位置）。用 `truncation="only_second" + doc_stride=128` 切多窗，各窗独立预测后取全局最高分 span。
2. **不过滤问题侧 token = F1 虚高**。模型可能把问题里的实体直接当答案（问题与答案共享实体时尤其常见）。必须只接受 `sequence_ids == 1`（上下文侧）的 token。

### 4.5.5 上下文构造必须回传"实际用到的段落"

`build_context()` 的返回值是 `(context_text, used_doc_ids)` 而非单个字符串。原因：E5 要把金标段落挪到首/中/尾，但长度预算可能把它直接挤出上下文 —— 此时 F1 暴跌是**截断**而非**位置**。回传 `used_doc_ids` 后，E5 才能同时报"金标保留率"，把两种效应分开（详见 3.7 与 5.5）。

### 4.5.6 延迟测量：预热 + 单线程 + batch=1

三个口径陷阱，任何一个没处理都会得出错误结论：

| 陷阱 | 现象 | 处理 |
|---|---|---|
| 不预热 | faiss 首调慢，会得出"numpy 比 faiss 快"的相反结论 | 预热一轮，5 轮取中位数 |
| 吞吐/延迟混测 | 同一份代码 batch=16 多线程 vs batch=1 单线程差 3–5 倍 | 指标用 batch，延迟单独 `benchmark_latency()` |
| int8 当"更快" | `bge-reranker` 的 int8 ONNX 在 1 线程下 0.74 s/pair，比 fp32 还慢；提到 18 线程才降到 0.14 s | 量化 kernel 依赖多线程，单线程口径下不能拿 int8 当加速论据 |

**因此第 5 章所有延迟数字都需附注："CPU 单线程、batch=1、预热后 3 轮中位数"。**

## 4.6 复现性措施

| 措施 | 做法 | 效果 |
|---|---|---|
| 随机性 | `seed=42` 全局固定，排序稳定化 | 同配置重跑逐位一致 |
| 置信区间 | `bootstrap_ci(n=1000, seed=42)` | 每个主结果带 95% CI |
| 超参 | 全部在 `config.yaml` | 报告第 4 章表格即配置快照 |
| 后端钉死 | int8 / fp32 权重二选一必须显式传 `--model-path` | 避免 `--encoder auto` 优先 fp32 导致 0.4 点差异 |

## 4.7 踩坑与解决（精选）

完整 40 余条见 `docs/pitfalls.md`，此处只列影响结论的 8 条：

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 数据换了编号，指标偏移却无报错 | 向量缓存只按"条数"命中 | 缓存键锚定语料 sha1 |
| 2 | 归一化消融两臂结果完全相同 | ONNX 图内默认归一化吞掉外部参数 | 参数透传 + 缓存键带 norm 标记 |
| 3 | α 曲线形状反常 | 分词器不同（单字+二元组 vs jieba） | 分词器进配置并随模型序列化 |
| 4 | 阅读器 F1 虚高 | 抽到了问题里的 token | 只接受 `sequence_ids==1` |
| 5 | E5 尾部 F1 崩到 0.21 | 金标被长度预算挤出上下文 | 回传 `used_doc_ids`，加跑 4000 档 |
| 6 | "重排不可用" | 单线程 batch=1 报出来的延迟 | 指标与延迟分开测 |
| 7 | 模型下不动（407 MB） | `hf-mirror.com` 302 到 `cas-bridge.xethub.hf.co`，该节点不通 | 换 `hf-mirror.net`（直出）+ 4 连接分段 |
| 8 | 权重加载失败 | 分段下载重试复用了旧 Range 起点 → part 体积超标 | 换 parts 数或中断后先删 part 文件 |

第 7、8 条不属于算法，但**耗掉了两天里的半天**——这条经验值得写进报告：在受限网络下，"能下载"是一个需要工程手段（HEAD 探 Location、分段续传、多镜像候选）才能达成的技术问题，而不是环境前提。

## 4.9 一个必须声明的口径问题

五组实验的**样本量并不相同**，横向读第 5 章时必须携带这一列：

| 实验 | split | $n$ | 原因 |
|---|---|---|---|
| E1 | smoke | 500 | 基线快速验证 |
| E2 / E3 / E6 | **full** | **3219** | 只要检索，成本低 |
| E4 / E5 | smoke | **100** | 含阅读器/重排，CPU 上是 $O(n\times\text{depth})$ 的前向 |

后果：**E1 与 E2 不能直接并列**。E1 的 smoke 数字是 Recall@5 0.934，而同一配置（α=1.0）在 full 上是 0.949 —— 1.5 个点的差异**全部来自样本不同**，不是方法改进。第 5 章的总表因此统一采用 full 口径的稠密行作为 E1 基线，并单独标注 smoke 数字。

同理，E4/E5 的 $n=100$ 使 Recall@5 的 95% CI 约 ±2–4 个点，**小差距（<2 点）不得下强结论**，应改看 MRR 与 Recall@1 这类对排序更敏感、方差更小的指标。

> 本章小结：在未启用 GPU、不训练、网络受限的三重约束下，最终达成的是"**单卡可复现的离线消融研究**"——所有数字可在 20 分钟内重跑，所有结论都带置信区间，所有工程陷阱都有记录与对策。代价是延迟结论只对 CPU 单线程成立，这一点在第 6 章的局限中说清。
