# 第 2 章 相关工作

> 分工 B 撰写。对应"调研"与"原理"两部分要求：从稀疏检索、稠密检索、
> 迟交互、排名融合到 RAG，最后说明本文实验在其中的位置。

## 2.1 稀疏检索：从布尔模型到 BM25

信息检索的第一代方法是**词项匹配**。布尔模型只判断"文档是否含查询词"，
无法排序；向量空间模型^[1]^把文档与查询表示为词项权重向量，
用余弦相似度排序，权重从 TF-IDF 逐步演化到带文档长度归一化的形式。
真正把"词频饱和"与"长度惩罚"写成概率模型的是 **BM25**：
Robertson 与 Sparck Jones 在 1976 年提出概率相关框架^[2]^，Robertson 与 Zaragoza 在 2009 年给出完整推导与工程化形式^[3]^，即今天搜索引擎与 Elasticsearch 的默认打分函数。

BM25 的两个关键设计直接对应两个经验事实（详见第 3 章公式）：

1. **词频饱和**：一个词在文档中出现 100 次并不比出现 10 次相关 10 倍，
   因此 `tf` 项在 `k1` 处收敛；
2. **文档长度归一化**：长文档天然更容易命中查询词，需按 `|d|/avgdl` 惩罚，
   参数 `b` 控制惩罚强度（`b=0` 表示不归一化）。

中文场景下 BM25 还有一个前置问题：**分词**。中文没有空格，
"南京市长江大桥"既可能切成"南京市/长江大桥"，也可能切成"南京/市长/江大桥"。
主流做法是词典分词（如 jieba）或字级 n-gram；后者不依赖词典、
对未登录词更鲁棒，代价是索引膨胀。本文的实现在 jieba 可用时用精确模式，
不可用时退化为"汉字单字 + 相邻二元组"，二者共用同一套打分逻辑。

稀疏检索的根本局限是**词不匹配（vocabulary mismatch）**：
问"如何治疗感冒"与文档"流感的防治方法"在词面上几乎无交集。
BM25 还有一个隐性偏差——它只对出现在查询中的词加权，
因此对**专名、数字、代码**这类稀有词非常敏感（idf 高），
这一点在混合检索中反而成了优势。

## 2.2 稠密检索：双塔与对比学习

稠密检索把查询与段落各编码成一个定长向量，用内积/余弦做近邻搜索。
早期 DSSM^[4]^用词哈希 + 双塔 MLP 做语义匹配；
BERT^[5]^出现后，ORQA、REALM 等工作把 BERT 用作检索器，
但受限于"需要为每个候选段落跑一次 BERT"的高延迟。

**DPR**^[6]^确立了现代双塔范式：
查询塔与段落塔共享 BERT 结构但参数独立，取 `[CLS]` 向量做内积，
用**批内负样本 + BM25 难负样本**做对比学习，配合 FAISS 做近似最近邻搜索，
在开放域问答上大幅超过 BM25。它的两个工程要点被后续工作沿用：
负样本质量决定上限（批内负样本的"假阴性"要用跨批次或去噪手段缓解，
如 RocketQA^[7]^在中文/英文检索上的跨批次负样本与去噪采样），
以及索引必须离线预建、只能对段落做一次编码。

**BGE**（C-Pack）^[8]^是目前中文检索最强的开源家族之一：
用大规模弱监督语料做对比预训练，再在高质量标注对上微调，
并提出了**非对称指令**——查询侧加"为这个句子生成表示以用于检索相关文章："
前缀，段落侧不加。这一设计使同一个模型能在"短查询—长段落"的不对称场景下
工作，本文直接采用 `bge-small-zh-v1.5`（4 层、512 维）作为稠密通道。

稠密检索的局限同样明显：语义相似不等于**答案正确**，
对专名、数字、罕见术语这类"高 idf"信号不敏感，
且需要 GPU 才能低延迟编码。这正好与 BM25 互补——
前者补语义泛化，后者补精确匹配，于是有了混合检索。

## 2.3 多向量与迟交互：ColBERT 一族

双塔把整段压成一个向量，信息损失不可避免。**ColBERT**^[9]^提出**迟交互（late interaction）**：
查询与文档都保留每个 token 的上下文向量，
相关性用 `MaxSim`——对每个查询 token 取它在文档 token 上的最大相似度再求和。
它在效果上接近 cross-encoder，同时保留了可预建索引的能力
（用倒排 + 压缩向量做候选剪枝）。ColBERTv2^[10]^进一步用残差压缩把存储降低一个数量级，并用去噪监督提升跨域泛化。

三种范式的权衡可以概括为一条"三角"：
**cross-encoder**^[11]^（查询—段落拼接后过 BERT）精度最高但必须在线逐对打分，
只能用于 top-k 重排；**双塔**可离线建索引、延迟最低但精度受限；
**迟交互**居中，用 token 级交互换回一部分精度。
本文把重排交给分工 C 的 cross-encoder，检索侧只比较双塔与 BM25，
正是在这个三角上做"召回"与"成本"的取舍。

## 2.4 排名融合与 RRF

混合检索的核心问题不是"两个分数谁大"，而是"如何合并两个**不可比**的分数"。
早期做法是分数归一化（min-max、z-score）后线性加权（CombSUM/CombMNZ）^[12]^，但归一化对分数分布敏感：
BM25 分数长尾、余弦相似度集中在 0.5–0.9 的窄区间，
一次归一化参数的偏差就能改变排序。

**RRF**（Reciprocal Rank Fusion）^[13]^绕开了这个问题：
只用名次，`score(d) = Σ 1/(k + rank(d))`，`k` 取 60 为经验值。
它的直觉是"多路都排在前面的文档更可信"，且常数 `k` 把名次差异压平，
使单路的第一名不会压倒另一路的第十名。RRF 因实现简单、无需训练、
无需调参，已成为工业界混合检索的默认融合方式
（Elasticsearch、Weaviate 等均内置 RRF）。

本文在 RRF 上引入**连续权重** α ∈ [0,1]：
`w_bm25 = 1−α, w_dense = α`，从而把"纯 BM25 / 等权融合 / 纯稠密"连成一条曲线，
用一次扫描回答"混合检索到底能带来多少增益、增益对权重有多敏感"（E2）。

## 2.5 检索增强生成（RAG）

**RAG**^[14]^把检索器与生成器端到端结合：
用 DPR 检索段落、用 BART 生成答案，并在生成时对边缘化后的段落做注意力。
FiD^[15]^改为"分别编码每个段落、在解码器侧拼接"，
使段落数不再受解码器长度限制；RETRO^[16]^把检索做到 token 级；
Atlas^[17]^系统研究了"检索器与生成器联合训练"的收益；
Self-RAG^[18]^引入反思 token，让模型自己决定"要不要检索、
检索到的段落是否相关"。

这一支文献反复确认了一个结论：**检索质量是 RAG 的性能上限**。
生成器再强，若金标段落没进上下文，抽取式任务的 EM 直接为 0；
而上下文里塞满噪声段落又会诱发"迷失在中间"（lost in the middle）^[19]^等位置偏差。
这正是本文把"检索"单独拎出来做消融、并同时报告
`Recall@k`（召回上限）与 `context_chars@5`（下游成本）的原因。

中文侧，CMRC2018^[20]^是抽取式阅读理解的代表数据集：
每条样本自带一个段落与段内答案跨度，因此**段落即金标**，
可以在零人工标注的前提下构造"问题→段落"的检索评测，
这也是本文选择它而非需要额外标注的检索数据集的原因。

## 2.6 本文的位置

把上述脉络放在一起，本文的实验设计对应三个具体缺口：

| 缺口 | 本文的做法 |
| --- | --- |
| 混合检索的增益常被"汇报为一个大数字"，缺少对融合权重的敏感度分析 | E2：α 从 0 扫到 1（0/0.2/0.4/0.5/0.6/0.8/1.0 共 7 个点，两端即单路基线），每点给 95% bootstrap CI |
| 切块策略常被当作工程细节，缺少"召回—成本"同框的证据 | E3：从整段到句级到 128/256/512 字（含重叠），同时报告 Recall、chunks/doc、上下文长度、延迟 |
| 复现常止于"跑通"，缺少可核对的中间产物 | 所有指标落 JSON（含运行环境与超参），核心模块有 13 项自检（`pytest -q`） |
